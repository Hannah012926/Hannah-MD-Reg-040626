The Agentic Medical Device Reviewer is a state-of-the-art, client-side web application designed to streamline and automate the regulatory review process for medical devices, specifically targeting FDA 510(k) submissions and Taiwan FDA (TFDA) premarket applications. Built using a modern React 19 and Vite architecture, the application leverages the power of Google's Gemini Large Language Models (LLMs) to analyze complex regulatory guidance documents, synthesize comprehensive reports, generate standardized templates, and provide interactive AI-driven features.
This technical specification details the architectural decisions, component structures, state management paradigms, and artificial intelligence integration strategies employed in the current implementation. The system is designed to be highly responsive, visually customizable through a unique "Painter Style" theming engine, and fully bilingual (English and Traditional Chinese). By encapsulating complex prompt engineering and API interactions within an intuitive user interface, the application empowers regulatory affairs professionals to drastically reduce the time required for document analysis and report generation.
2. System Architecture
The application follows a monolithic frontend architecture, operating entirely within the client's browser while interfacing directly with the Google Gemini API via secure, serverless calls.
2.1 Architectural Principles
Client-Heavy Processing: To minimize server infrastructure costs and reduce latency, all UI rendering, state management, and markdown parsing are handled client-side.
Stateless AI Integration: The application does not persist user data or AI conversation history to a backend database. All state is maintained in the React component tree or React Context, ensuring data privacy for sensitive regulatory documents.
Component-Driven Design: The UI is constructed using atomic design principles, heavily utilizing Shadcn UI components to ensure visual consistency and accessibility.
Separation of Concerns: The application strictly separates the UI layer (React components), the global state layer (React Context), and the service layer (Gemini API integration).

Core Function: generateContent
Parameters:

prompt: The user's input combined with the specific task instructions.

Security: The GEMINI_API_KEY is accessed via process.env.GEMINI_API_KEY, which is injected at build time by Vite's define configuration.
Error Handling: The function throws standard JavaScript errors if the API key is missing or if the network request fails, which are then caught and handled by the calling UI components.

6. Feature Specifications (The Tabs)
The application's core functionality is divided into four distinct tabs, each representing a step in the regulatory review workflow.
6.1 Guidance Analysis & Research Tab (GuidanceAnalysisTab.tsx)
Purpose: To ingest raw regulatory guidance documents, perform external research, and synthesize a comprehensive summary report.
Component State:
input: The raw text or markdown pasted by the user.
prompt: The customizable instruction set for the LLM.
localModel: Allows the user to override the global model specifically for this task.
result: The markdown string returned by the API.
isLoading: Boolean flag to manage UI loading states.
Workflow:
The user pastes a guidance document into the Textarea.
Upon clicking "Analyze & Generate Report", handleGenerate is triggered.
A systemInstruction is constructed enforcing the persona ("expert Medical Device Regulatory Affairs Specialist") and the globally selected language.
The generateContent service is called with useSearch: true. This is a critical architectural decision: by enabling Google Search Grounding, the model can look up recent FDA 510(k) summaries, ISO standards, and updated guidance that may not be present in its base training data.
The result is stored in state and displayed in a dual-pane view (Edit mode via Textarea and Preview mode via react-markdown).
A "Download Markdown" button allows the user to export the result as a .md file using the URL.createObjectURL browser API.
6.2 Template-based Report Tab (TemplateReportTab.tsx)
Purpose: To take the comprehensive research from the previous step and format it strictly according to a predefined regulatory template (e.g., the TFDA Orthopedic External Fixators checklist).
Component State:
previousReport: The input data (ideally pasted from Tab 1).
template: The structural template. Initialized with a massive DEFAULT_TEMPLATE constant containing the TFDA guidelines.
prompt, localModel, result, isLoading: Standard execution state variables.
Workflow:
The user provides the source material and the desired template. A "Use Default Template" button quickly restores the TFDA checklist if the user accidentally modifies it.
The handleGenerate function concatenates the prompt, the template, and the previous report.
Unlike Tab 1, useSearch is set to false. This is intentional; this step is about formatting and mapping existing data to a structure, not hallucinating or researching new information.
The output is rendered in the standard Edit/Preview dual-pane interface.
6.3 Skill Creator Tab (SkillCreatorTab.tsx)
Purpose: To generate a skill.md file that defines a new AI agent skill based on the structure of the medical device guidance. This is a meta-feature, allowing the application to help build other AI tools.
Component State:
inputGuidance: The structural reference for the new skill.
prompt: Hardcoded to request a standard skill-creator format (YAML frontmatter) and the inclusion of "3 additional WOW features".
Workflow:
The systemInstruction enforces the persona of an "expert AI Agent Skill Creator" and mandates the output of a valid markdown file with YAML frontmatter (name and description).
The Gemini model analyzes the input guidance and extrapolates a reusable skill definition, inventing three novel features that would enhance an agent possessing this skill.
The resulting markdown is highly structured and ready to be downloaded as skill.md for use in other agentic frameworks (like Anthropic's Claude Code or similar platforms).
6.4 WOW AI Features Tab (WowFeaturesTab.tsx)
Purpose: To provide interactive, high-value AI utilities based on a shared context document (either the original guidance or the generated report).
This tab is the most complex, housing three distinct AI features within a responsive CSS Grid layout.
Shared State:
context: A master Textarea where the user pastes the foundational document. All three features rely on this context.
Feature 1: Interactive Q&A Chatbot
State: chatInput (current message), chatHistory (array of message objects with role and text), isChatting (loading state).
Implementation: Uses a ScrollArea to display the conversation history. When the user sends a message, the handleChat function appends the user's message to the history, constructs a prompt containing the master context and the user's question, and calls the Gemini API. The response is appended to the history as an 'ai' role.
UI: Messages are styled conditionally based on their role, with user messages appearing on the right (primary color) and AI messages on the left (muted color).
Feature 2: Auto-generate Submission Checklist
State: checklist (array of objects: { item: string, done: boolean }), isGeneratingChecklist.
Implementation: The prompt specifically requests "ONLY a JSON array of strings".
Parsing Logic: Because LLMs occasionally wrap JSON in markdown code blocks (e.g., json ...), the handleGenerateChecklist function uses a regular expression (/\[.*\]/s) to safely extract the array. If the regex fails, it falls back to splitting the response by newlines and stripping bullet points.
UI: Renders an interactive list of checkboxes. Toggling a checkbox updates the done boolean in the state, applying a strikethrough line-through style to the text.
Feature 3: AI Compliance Gap Analysis
State: gapAnalysis (markdown string), isGeneratingGap.
Implementation: Instructs the model to perform a critical review of the context, identifying missing information, potential regulatory risks, and areas needing clarification.
UI: Renders the resulting markdown using react-markdown within a scrollable card.
7. Data Flow & Interaction Models
The application relies on a unidirectional data flow paradigm typical of React applications.
User Input: The user interacts with Shadcn UI components (Textareas, Selects, Buttons).
Local State Update: onChange handlers update local component state (e.g., setInput).
Action Trigger: The user clicks a primary action button (e.g., "Generate").
API Invocation: The component's async handler constructs the prompt by interpolating local state variables and global context variables (like language). It calls geminiService.generateContent.
Loading State: While awaiting the network response, isLoading is set to true, disabling the button and rendering a spinning Loader2 icon.
Response Handling: The promise resolves, the resulting text is stored in the component's result state, and isLoading is set to false.
UI Re-render: React automatically re-renders the component, displaying the new result in the Markdown preview and Textarea.

9. Security & Privacy Considerations
Given the nature of medical device regulatory documents, security and privacy are paramount.
No Backend Storage: The application does not have a backend database. Documents pasted into the application remain in the browser's memory and are only transmitted to the Google Gemini API during active generation requests.
Ephemeral State: Refreshing the browser clears all application state, including pasted documents and generated reports.
API Key Management: The GEMINI_API_KEY is injected at build time via environment variables. In a production deployment (like Google Cloud Run), this key should be restricted via Google Cloud IAM to only allow requests originating from the application's specific domain, preventing unauthorized use of the quota.
Cross-Site Scripting (XSS) Prevention: The react-markdown library is used to render AI output. By default, this library safely escapes raw HTML, preventing malicious scripts injected by the LLM (or via prompt injection) from executing in the user's browser.
10. Future Extensibility
The architecture is designed to be highly modular, allowing for rapid future expansion.
Adding New Painter Themes: To add a new theme, a developer simply adds a new object to the PAINTER_STYLES array in painter-styles.ts and defines the corresponding .theme-[name] CSS class in index.css with the desired HSL color variables.
Adding New LLM Models: New Gemini models (or even models from other providers if the service layer is expanded) can be added by updating the Model type in store.tsx and adding a new <SelectItem> in the App.tsx sidebar.
Adding New Workflow Tabs: A new feature can be added by creating a new component in src/components/tabs/, adding a new <TabsTrigger> in the App.tsx navigation bar, and mapping it to a <TabsContent> block.

1. Executive Summary
The Agentic Medical Device Reviewer is a state-of-the-art, client-side Single Page Application (SPA) designed to revolutionize the regulatory review and drafting process for medical devices. Specifically targeting complex regulatory frameworks such as the US FDA 510(k) submissions and the Taiwan FDA (TFDA) premarket applications (查驗登記), the application leverages the advanced reasoning and generative capabilities of Google's Gemini Large Language Models (LLMs).
Transitioning from traditional, manual document review processes, this application introduces an "agentic" workflow where AI assists regulatory affairs professionals in analyzing extensive guidance documents, synthesizing comprehensive reports, formatting data into strict regulatory templates, and generating interactive compliance tools.
The system is built on a modern, high-performance web stack utilizing React 19, Vite 6, and Tailwind CSS v4. It features a highly customizable user interface with 20 distinct "Painter Styles" for personalized theming, native bilingual support (English and Traditional Chinese), and a modular tab-based architecture. By encapsulating complex prompt engineering, API integrations, and state management within an intuitive UI, the Agentic Medical Device Reviewer drastically reduces the time and cognitive load required for medical device regulatory compliance.

Client-Heavy Processing: To minimize server costs and eliminate network latency associated with round-trip HTML rendering, all UI rendering, state management, markdown parsing, and user interactions are handled client-side by the React engine.
Stateless AI Integration: The application does not persist user data, uploaded guidance documents, or AI conversation history to a centralized backend database. All state is maintained ephemerally in the React component tree or the global React Context. Component-Driven Design: The User Interface is constructed using atomic design principles. It heavily utilizes Shadcn UI components—which are built on top of Radix UI primitives—to ensure visual consistency, keyboard accessibility, and screen-reader compatibility.
Separation of Concerns: The codebase strictly separates the UI presentation layer (React components in src/components), the global state layer (src/store.tsx), and the external service layer (src/services/geminiService.ts).

6. AI Integration Layer
The src/services/geminiService.ts module isolates all interactions with the Google Gemini API. This abstraction ensures that UI components remain agnostic to the underlying network requests, SDK specifics, and authentication mechanisms.
6.1 Core Function: generateContent
This asynchronous function is the sole conduit for AI generation in the application.
code
TypeScript
import { GoogleGenAI } from '@google/genai';

export async function generateContent(
  model: string,
  prompt: string,
  systemInstruction?: string,
  useSearch: boolean = false
) {
  const apiKey = process.env.GEMINI_API_KEY;
  if (!apiKey) throw new Error('GEMINI_API_KEY is not set');

  const ai = new GoogleGenAI({ apiKey });
  const config: any = {};
  
  if (systemInstruction) config.systemInstruction = systemInstruction;
  if (useSearch) config.tools = [{ googleSearch: {} }];

  const response = await ai.models.generateContent({
    model,
    contents: prompt,
    config,
  });

  return response.text || '';
}
6.2 Key AI Features Utilized
System Instructions: Used extensively to define the persona of the AI (e.g., "expert Medical Device Regulatory Affairs Specialist") and to strictly enforce the output language based on the user's global language setting.
Google Search Grounding (useSearch): When enabled (specifically in the Guidance Analysis tab), this injects the { googleSearch: {} } tool into the configuration. This allows the Gemini model to bypass its training data cutoff and query the live internet for recent FDA 510(k) summaries, updated ISO standards, and contemporary regulatory guidance, drastically improving the accuracy and relevance of the reports.
Model Overrides: While a global model is set in the sidebar, the generateContent function accepts a model parameter. This allows individual tabs to override the global setting if a specific task requires a different model tier (e.g., using gemini-3.1-pro-preview for complex gap analysis, but gemini-2.5-flash for rapid checklist generation).
7. Core Modules & User Interface
The application utilizes a classic, highly functional dashboard layout, divided into a fixed sidebar for global settings and a main content area for task execution.
7.1 Layout & Navigation (App.tsx)
Sidebar (w-64): The sidebar is persistent and contains controls that mutate the global AppContext. It includes the Theme Toggle (Light/Dark), Language Selector (English/Traditional Chinese), Painter Style Selector, and Global Model Selector.
Main Content Area: The main area utilizes the Shadcn Tabs component to navigate between four distinct functional modules. The TabsList is sticky at the top, ensuring navigation is always accessible, while the TabsContent is wrapped in a ScrollArea to handle overflow gracefully.
7.2 Module 1: Guidance Analysis & Research (GuidanceAnalysisTab.tsx)
Purpose: To ingest raw regulatory guidance documents, perform external research via Google Search Grounding, and synthesize a comprehensive summary report.
Workflow & State:
Input: The user pastes a guidance document into a large Textarea (input state).
Configuration: The user can modify the default prompt and override the localModel.
Execution: Clicking "Analyze & Generate Report" triggers handleGenerate. The systemInstruction enforces the persona and language. The generateContent service is called with useSearch: true.
Display: The result is stored in the result state. It is displayed in a dual-pane view using nested Tabs: an "Edit" mode featuring a raw Textarea for manual adjustments, and a "Preview" mode utilizing react-markdown to render the formatted HTML.
Export: A "Download Markdown" button allows the user to export the result as a .md file using the URL.createObjectURL browser API.
7.3 Module 2: Template-based Report (TemplateReportTab.tsx)
Purpose: To take the comprehensive research from the previous step and format it strictly according to a predefined regulatory template (e.g., the TFDA Orthopedic External Fixators checklist).
Workflow & State:
Input: The user pastes the report from Tab 1 into the previousReport Textarea.
Template Management: The template state is initialized with a massive DEFAULT_TEMPLATE constant containing the official TFDA guidelines for Orthopedic External Fixators. A "Use Default Template" button allows users to quickly restore this if they accidentally modify it.
Execution: The handleGenerate function concatenates the custom prompt, the template, and the previous report. Crucially, useSearch is set to false. This step is strictly about formatting and mapping existing data to a structure, not hallucinating or researching new information.
Display & Export: The output is rendered in the standard Edit/Preview dual-pane interface with download capabilities.
7.4 Module 3: Skill Creator (SkillCreatorTab.tsx)
Purpose: A meta-feature designed to generate a skill.md file. This file defines a new AI agent skill based on the structure of the medical device guidance, allowing the application to help build other AI tools.
Workflow & State:
Input: The user pastes the structural reference for the new skill into inputGuidance.
Execution: The systemInstruction enforces the persona of an "expert AI Agent Skill Creator". It mandates the output of a valid markdown file with YAML frontmatter (containing name and description keys). Furthermore, the prompt instructs the LLM to invent "3 additional WOW features" that would enhance an agent possessing this skill.
Output: The resulting markdown is highly structured, adhering to standard agentic framework specifications (like Anthropic's Claude Code or similar platforms), and is ready for download.
7.5 Module 4: WOW AI Features (WowFeaturesTab.tsx)
Purpose: To provide interactive, high-value AI utilities based on a shared context document. This tab demonstrates the power of LLMs beyond simple text generation.
This tab houses three distinct AI features within a responsive CSS Grid layout. All three features rely on a shared context state (a master Textarea where the user pastes the foundational document).
Feature A: Interactive Q&A Chatbot
Implementation: Maintains a chatHistory array of message objects ({ role: 'user' | 'ai', text: string }).
Execution: When the user sends a message, handleChat appends it to the history, constructs a prompt containing the master context and the user's question, and calls the Gemini API. The response is appended as an 'ai' role.
UI: Messages are styled conditionally based on their role, utilizing primary colors for user messages and muted backgrounds for AI responses. The chat window auto-scrolls within a ScrollArea.
Feature B: Auto-generate Submission Checklist
Implementation: The prompt explicitly requests "ONLY a JSON array of strings" representing actionable submission items extracted from the context.
Parsing Logic: Because LLMs occasionally wrap JSON in markdown code blocks, the handleGenerateChecklist function uses a regular expression (/\[.*\]/s) to safely extract the array. If the regex fails, a fallback mechanism splits the response by newlines and strips bullet points.
UI: Renders an interactive list of checkboxes. Toggling a checkbox updates a done boolean in the state, applying a strikethrough (line-through) CSS class to the text, providing immediate visual feedback.
Feature C: AI Compliance Gap Analysis
Implementation: Instructs the model to perform a critical review of the context, identifying missing information, potential regulatory risks, and areas needing clarification before submission.
UI: Renders the resulting markdown using react-markdown within a scrollable card, providing a clear, formatted audit report.

9. Security & Privacy Considerations
Given the highly sensitive nature of medical device regulatory documents (which may contain proprietary IP, unreleased product specifications, or clinical data), security and privacy are paramount architectural drivers.
No Backend Storage: The application operates entirely client-side. Documents pasted into the application remain in the browser's memory and are only transmitted to the Google Gemini API via secure HTTPS during active generation requests. There is no database, no logging of user inputs, and no persistence of generated reports on the host server.
Ephemeral State: Refreshing the browser clears all application state. This "amnesic" design ensures that sensitive data is not accidentally left behind on shared computers.
Cross-Site Scripting (XSS) Prevention: The react-markdown library is used to render all AI output. By default, this library safely escapes raw HTML. This prevents malicious scripts—potentially injected by the LLM via hallucination or through adversarial prompt injection in the source documents—from executing in the user's browser.
API Key Management: The GEMINI_API_KEY is injected at build time via Vite's environment variables (process.env.GEMINI_API_KEY). While this exposes the key to the client bundle, in a production deployment (like Google Cloud Run), this key must be restricted via Google Cloud IAM/API restrictions to only allow requests originating from the application's specific HTTP referrers, preventing unauthorized use of the quota by third parties.
10. Deployment & DevOps
The application is designed to be deployed as a static site or within a lightweight containerized environment.
Build Process: Running npm run build triggers Vite to compile the React application, transpile TypeScript, process Tailwind CSS, and bundle the assets using Rollup. The output is a highly optimized set of static files in the dist/ directory.
Hosting: Because there is no Node.js backend required at runtime, the application can be hosted on any static file server (e.g., AWS S3 + CloudFront, Vercel, Netlify, GitHub Pages) or packaged into a lightweight Nginx Docker container for deployment to Google Cloud Run.
Environment Variables: The build process requires a .env file containing the VITE_GEMINI_API_KEY (or GEMINI_API_KEY depending on the exact Vite config mapping) to successfully compile the service layer.
11. Future Extensibility
The architecture is designed to be highly modular, allowing for rapid future expansion with minimal technical debt.
Adding New Painter Themes: To add a new theme, a developer simply adds a new object to the PAINTER_STYLES array in src/lib/painter-styles.ts and defines the corresponding .theme-[name] CSS class in src/index.css with the desired HSL color variables. No React code needs to be modified.
Adding New LLM Models: New Gemini models (or models from other providers like Anthropic or OpenAI, if the service layer is abstracted further) can be added by updating the Model type in src/store.tsx and adding a new <SelectItem> in the App.tsx sidebar.
Adding New Workflow Tabs: A new feature can be added by creating a new component file in src/components/tabs/, adding a new <TabsTrigger> in the App.tsx navigation bar, and mapping it to a new <TabsContent> block. The modular design ensures that new tabs do not interfere with the state or logic of existing tabs.
12. Comprehensive Follow-Up Questions
To ensure the continued success, security, scalability, and regulatory compliance of the Agentic Medical Device Reviewer, the following 20 comprehensive questions should be evaluated by the product, engineering, and legal teams:
Architecture & Performance
State Persistence: Currently, refreshing the page results in total data loss. Should we implement an opt-in localStorage or IndexedDB caching mechanism for the global context and tab states to prevent accidental data loss during long review sessions?
Web Workers for Markdown: As generated regulatory reports grow to 5000+ words, synchronous markdown parsing on the main thread might cause UI stutter. Should we offload react-markdown rendering to a Web Worker?
Streaming Responses: The current implementation waits for the entire Gemini response before updating the UI. Should we implement the generateContentStream API to provide a typewriter-effect, reducing perceived latency and improving UX for long generations?
Bundle Size Optimization: We are importing the entirety of lucide-react and react-markdown. Have we audited the Vite build output to ensure tree-shaking is working correctly, or should we implement lazy loading for specific tabs?
Native Document Parsing: The original prompt mentioned PDF uploads. Since this is a client-side app, should we integrate pdfjs-dist or mammoth.js to extract text from PDFs and DOCX files directly in the browser before sending the text to the LLM?
AI & Prompt Engineering
Search Grounding Costs: Google Search Grounding is enabled on Tab 1. What are the cost implications of this at scale, and should we provide a user toggle to disable it for simpler queries to save on API credits?
Context Window Limits: Medical device guidance documents can be hundreds of pages long. How should the application handle inputs that exceed the token limit of the selected Gemini model? Should we implement client-side chunking and map-reduce summarization?
Hallucination Mitigation: In the "Gap Analysis" feature, how can we mathematically or programmatically verify that the AI isn't hallucinating regulatory requirements that don't exist in the TFDA guidelines?
Prompt Versioning: The prompts are currently hardcoded in the React components. Should we move these to a separate configuration file or a remote CMS so regulatory experts can tweak them without requiring a code deployment?
Structured Output Enforcement: The regex fallback for JSON extraction in the Checklist feature is potentially brittle. Should we utilize Gemini's responseSchema configuration to guarantee a strict JSON array output at the API level?
User Experience (UX) & Design
Mobile Responsiveness: The current layout uses a fixed 64-width sidebar. How should this UI adapt for tablet or mobile users? Should the sidebar collapse into a hamburger menu or a bottom navigation bar?
Accessibility (a11y) Audits: Have we audited the Shadcn UI components and our custom color themes (especially the high-contrast painter themes like Picasso or Warhol) for WCAG AA color contrast compliance?
Export Formats: Currently, we only export to Markdown. Should we integrate a library like jspdf or html2pdf.js to allow users to download their final reports as formatted, professional PDF documents?
Chat History Management: In the WOW Features tab, the chat history grows indefinitely. Should we implement a "Clear Chat" button and a mechanism to prune older messages to save context tokens and prevent context-window overflow?
Theme Persistence: Should the user's selected Painter Style, Language, and Dark/Light mode preference be saved to their browser preferences (localStorage) so it persists across sessions automatically?
Security & Compliance
Data Confidentiality Warnings: Even though we don't store data, sending unreleased medical device specs to Google's API might violate corporate NDAs. Do we need to implement a mandatory warning modal advising users not to paste Proprietary Information (PII/PHI) before they can use the app?
Enterprise API Keys: Currently, the app uses a single environment API key. For a SaaS model, should we implement an OAuth flow allowing enterprise users to bring their own Google Cloud project API keys (BYOK)?
Content Moderation: Should we implement Gemini's safety settings to ensure the model doesn't generate inappropriate content, or should we explicitly lower the safety thresholds to ensure it doesn't falsely flag legitimate medical terminology (e.g., surgical procedures) as "gore"?
Product & Domain-Specific (FDA/TFDA)
Template Updates: Regulatory templates change frequently. How will we maintain the DEFAULT_TEMPLATE in Tab 2? Should this be fetched dynamically from a GitHub repository or a database rather than hardcoded?
Predicate Device Database Integration: For 510(k) reviews, identifying predicate devices is crucial. Could we integrate a direct API call to the FDA's openFDA database to cross-reference the LLM's findings in real-time, providing clickable links to the actual predicate device records?
