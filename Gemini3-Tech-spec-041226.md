Technical Specification: Agentic Medical Device Reviewer
1. Executive Summary
The Agentic Medical Device Reviewer is a state-of-the-art, client-side web application designed to streamline and automate the regulatory review process for medical devices, specifically targeting FDA 510(k) submissions and Taiwan FDA (TFDA) premarket applications. Built using a modern React 19 and Vite architecture, the application leverages the power of Google's Gemini Large Language Models (LLMs) to analyze complex regulatory guidance documents, synthesize comprehensive reports, generate standardized templates, and provide interactive AI-driven features.
This technical specification details the architectural decisions, component structures, state management paradigms, and artificial intelligence integration strategies employed in the current implementation. The system is designed to be highly responsive, visually customizable through a unique "Painter Style" theming engine, and fully bilingual (English and Traditional Chinese). By encapsulating complex prompt engineering and API interactions within an intuitive user interface, the application empowers regulatory affairs professionals to drastically reduce the time required for document analysis and report generation.
2. System Architecture
The application follows a monolithic frontend architecture, operating entirely within the client's browser while interfacing directly with the Google Gemini API via secure, serverless calls.
2.1 Architectural Principles
Client-Heavy Processing: To minimize server infrastructure costs and reduce latency, all UI rendering, state management, and markdown parsing are handled client-side.
Stateless AI Integration: The application does not persist user data or AI conversation history to a backend database. All state is maintained in the React component tree or React Context, ensuring data privacy for sensitive regulatory documents.
Component-Driven Design: The UI is constructed using atomic design principles, heavily utilizing Shadcn UI components to ensure visual consistency and accessibility.
Separation of Concerns: The application strictly separates the UI layer (React components), the global state layer (React Context), and the service layer (Gemini API integration).

3. Technology Stack
The technology stack was selected to prioritize developer velocity, runtime performance, and modern UI/UX paradigms.
3.1 Core Frameworks
React 19: The latest version of React is used for building the user interface, leveraging functional components and hooks for state and lifecycle management.
Vite 6: Used as the build tool and development server. Vite provides extremely fast Hot Module Replacement (HMR) and optimized production builds using Rollup.
TypeScript 5.8: Provides static typing across the application, significantly reducing runtime errors and improving developer experience through enhanced IDE autocompletion.
3.2 Styling and UI Library
Tailwind CSS v4: A utility-first CSS framework used for all styling. Version 4 introduces a streamlined configuration process directly within the CSS file using @theme directives.
Shadcn UI: A collection of re-usable components built on top of Radix UI primitives and Tailwind CSS. It provides accessible, unstyled components that are customized via Tailwind classes.
Lucide React: A comprehensive icon library used for all iconography within the application, ensuring a consistent visual language.
3.3 Artificial Intelligence and Data Processing
@google/genai (v1.29.0): The official Google Gen AI SDK used to interface with the Gemini models. It supports advanced features like system instructions and Google Search Grounding.
React Markdown: Used to safely render the markdown output generated by the Gemini models into HTML.
@tailwindcss/typography: A Tailwind plugin that provides the prose class, which automatically styles raw HTML output (like that generated by react-markdown) with beautiful, readable typographic defaults.
4. Core Components & Modules
4.1 Global State Management (store.tsx)
Given the application's scope, Redux or Zustand were deemed unnecessarily complex. Instead, the application utilizes React's native Context API combined with the useState hook to manage global application state.
State Interface Definition:
code
TypeScript
export type Theme = 'light' | 'dark';
export type Language = 'en' | 'zh-TW';
export type Model = 'gemini-2.5-flash' | 'gemini-3.1-flash-preview' | 'gemini-3.1-pro-preview';

interface AppState {
  theme: Theme;
  setTheme: (theme: Theme) => void;
  language: Language;
  setLanguage: (lang: Language) => void;
  painterStyle: string;
  setPainterStyle: (style: string) => void;
  model: Model;
  setModel: (model: Model) => void;
}
Implementation Details:
The AppProvider component wraps the entire application tree in main.tsx.
It initializes default values: theme (light), language (zh-TW), painterStyle (default), and model (gemini-3.1-pro-preview).
A custom hook, useAppContext, is exported to allow any deeply nested component to access and mutate the global state without prop drilling.
4.2 AI Service Layer (geminiService.ts)
This module isolates all interactions with the Google Gemini API, ensuring that UI components remain agnostic to the underlying network requests and SDK specifics.
Core Function: generateContent
Parameters:
model: The specific Gemini model to use (passed from global state or local override).
prompt: The user's input combined with the specific task instructions.
systemInstruction (optional): High-level directives dictating the persona and output language.
useSearch (optional): A boolean flag that, when true, injects the { googleSearch: {} } tool into the configuration, enabling the model to ground its responses in real-time web data.
Security: The GEMINI_API_KEY is accessed via process.env.GEMINI_API_KEY, which is injected at build time by Vite's define configuration.
Error Handling: The function throws standard JavaScript errors if the API key is missing or if the network request fails, which are then caught and handled by the calling UI components.
4.3 Theming Engine (painter-styles.ts & index.css)
One of the most unique features of this application is its dynamic theming engine, which allows users to apply color palettes inspired by 20 famous painters.
CSS Variable Architecture:
The application uses a semantic color system defined in index.css. Base variables include --background, --foreground, --primary, --card, and --border.
Painter Style Implementation:
painter-styles.ts exports an array of objects containing the id, name, and class for each painter (e.g., { id: 'van-gogh', name: 'Vincent van Gogh', class: 'theme-van-gogh' }).
In index.css, specific CSS classes override the root variables. For example:
code
CSS
.theme-van-gogh {
  --background: 215 50% 15%; /* Deep starry night blue */
  --foreground: 50 100% 85%;
  --primary: 45 100% 50%;    /* Sunflower yellow */
  --primary-foreground: 215 50% 15%;
  --card: 215 40% 20%;
  --border: 215 40% 30%;
}
Dynamic Application: In App.tsx, a useEffect hook listens for changes to the painterStyle and theme state variables. It directly manipulates the classList of document.documentElement (the <html> tag), removing old theme classes and appending the newly selected one. This approach ensures that Tailwind's utility classes (like bg-primary) instantly reflect the new color palette without requiring a page reload.
5. User Interface & Layout (App.tsx)
The application utilizes a classic dashboard layout, divided into a fixed sidebar for global settings and a main content area for task execution.
5.1 Sidebar Configuration
The sidebar (w-64) is persistent and contains the following controls, which directly mutate the global AppContext:
Theme Toggle: A switch to alternate between light and dark modes.
Language Selector: A dropdown to switch between English and Traditional Chinese. This selection dynamically updates the UI text (via a localized t object) and alters the systemInstruction sent to the Gemini API.
Painter Style Selector: A dropdown containing the 20 artistic themes.
Global Model Selector: A dropdown to set the default Gemini model for all tabs.
5.2 Main Content Area
The main area utilizes the Shadcn Tabs component to navigate between four distinct functional modules. The TabsList is sticky at the top, while the TabsContent is wrapped in a ScrollArea to handle overflow gracefully.
6. Feature Specifications (The Tabs)
The application's core functionality is divided into four distinct tabs, each representing a step in the regulatory review workflow.
6.1 Guidance Analysis & Research Tab (GuidanceAnalysisTab.tsx)
Purpose: To ingest raw regulatory guidance documents, perform external research, and synthesize a comprehensive summary report.
Component State:
input: The raw text or markdown pasted by the user.
prompt: The customizable instruction set for the LLM.
localModel: Allows the user to override the global model specifically for this task.
result: The markdown string returned by the API.
isLoading: Boolean flag to manage UI loading states.
Workflow:
The user pastes a guidance document into the Textarea.
Upon clicking "Analyze & Generate Report", handleGenerate is triggered.
A systemInstruction is constructed enforcing the persona ("expert Medical Device Regulatory Affairs Specialist") and the globally selected language.
The generateContent service is called with useSearch: true. This is a critical architectural decision: by enabling Google Search Grounding, the model can look up recent FDA 510(k) summaries, ISO standards, and updated guidance that may not be present in its base training data.
The result is stored in state and displayed in a dual-pane view (Edit mode via Textarea and Preview mode via react-markdown).
A "Download Markdown" button allows the user to export the result as a .md file using the URL.createObjectURL browser API.
6.2 Template-based Report Tab (TemplateReportTab.tsx)
Purpose: To take the comprehensive research from the previous step and format it strictly according to a predefined regulatory template (e.g., the TFDA Orthopedic External Fixators checklist).
Component State:
previousReport: The input data (ideally pasted from Tab 1).
template: The structural template. Initialized with a massive DEFAULT_TEMPLATE constant containing the TFDA guidelines.
prompt, localModel, result, isLoading: Standard execution state variables.
Workflow:
The user provides the source material and the desired template. A "Use Default Template" button quickly restores the TFDA checklist if the user accidentally modifies it.
The handleGenerate function concatenates the prompt, the template, and the previous report.
Unlike Tab 1, useSearch is set to false. This is intentional; this step is about formatting and mapping existing data to a structure, not hallucinating or researching new information.
The output is rendered in the standard Edit/Preview dual-pane interface.
6.3 Skill Creator Tab (SkillCreatorTab.tsx)
Purpose: To generate a skill.md file that defines a new AI agent skill based on the structure of the medical device guidance. This is a meta-feature, allowing the application to help build other AI tools.
Component State:
inputGuidance: The structural reference for the new skill.
prompt: Hardcoded to request a standard skill-creator format (YAML frontmatter) and the inclusion of "3 additional WOW features".
Workflow:
The systemInstruction enforces the persona of an "expert AI Agent Skill Creator" and mandates the output of a valid markdown file with YAML frontmatter (name and description).
The Gemini model analyzes the input guidance and extrapolates a reusable skill definition, inventing three novel features that would enhance an agent possessing this skill.
The resulting markdown is highly structured and ready to be downloaded as skill.md for use in other agentic frameworks (like Anthropic's Claude Code or similar platforms).
6.4 WOW AI Features Tab (WowFeaturesTab.tsx)
Purpose: To provide interactive, high-value AI utilities based on a shared context document (either the original guidance or the generated report).
This tab is the most complex, housing three distinct AI features within a responsive CSS Grid layout.
Shared State:
context: A master Textarea where the user pastes the foundational document. All three features rely on this context.
Feature 1: Interactive Q&A Chatbot
State: chatInput (current message), chatHistory (array of message objects with role and text), isChatting (loading state).
Implementation: Uses a ScrollArea to display the conversation history. When the user sends a message, the handleChat function appends the user's message to the history, constructs a prompt containing the master context and the user's question, and calls the Gemini API. The response is appended to the history as an 'ai' role.
UI: Messages are styled conditionally based on their role, with user messages appearing on the right (primary color) and AI messages on the left (muted color).
Feature 2: Auto-generate Submission Checklist
State: checklist (array of objects: { item: string, done: boolean }), isGeneratingChecklist.
Implementation: The prompt specifically requests "ONLY a JSON array of strings".
Parsing Logic: Because LLMs occasionally wrap JSON in markdown code blocks (e.g., json ...), the handleGenerateChecklist function uses a regular expression (/\[.*\]/s) to safely extract the array. If the regex fails, it falls back to splitting the response by newlines and stripping bullet points.
UI: Renders an interactive list of checkboxes. Toggling a checkbox updates the done boolean in the state, applying a strikethrough line-through style to the text.
Feature 3: AI Compliance Gap Analysis
State: gapAnalysis (markdown string), isGeneratingGap.
Implementation: Instructs the model to perform a critical review of the context, identifying missing information, potential regulatory risks, and areas needing clarification.
UI: Renders the resulting markdown using react-markdown within a scrollable card.
7. Data Flow & Interaction Models
The application relies on a unidirectional data flow paradigm typical of React applications.
User Input: The user interacts with Shadcn UI components (Textareas, Selects, Buttons).
Local State Update: onChange handlers update local component state (e.g., setInput).
Action Trigger: The user clicks a primary action button (e.g., "Generate").
API Invocation: The component's async handler constructs the prompt by interpolating local state variables and global context variables (like language). It calls geminiService.generateContent.
Loading State: While awaiting the network response, isLoading is set to true, disabling the button and rendering a spinning Loader2 icon.
Response Handling: The promise resolves, the resulting text is stored in the component's result state, and isLoading is set to false.
UI Re-render: React automatically re-renders the component, displaying the new result in the Markdown preview and Textarea.
8. Internationalization (i18n)
The application implements a lightweight, custom internationalization system without relying on heavy external libraries like react-i18next.
Global State: The language variable ('en' or 'zh-TW') is stored in the AppContext.
Translation Dictionaries: Inside each component, a local t object is defined. For example:
code
TypeScript
const t = {
  title: language === 'en' ? 'Skill Creator' : '技能建立器',
  generateBtn: language === 'en' ? 'Generate Skill.md' : '生成 Skill.md',
};
Prompt Localization: The selected language is dynamically injected into the systemInstruction sent to the Gemini API: Your output language must be ${language === 'en' ? 'English' : 'Traditional Chinese (繁體中文)'}. This ensures that not only the UI, but also the AI-generated content, matches the user's preference.
9. Security & Privacy Considerations
Given the nature of medical device regulatory documents, security and privacy are paramount.
No Backend Storage: The application does not have a backend database. Documents pasted into the application remain in the browser's memory and are only transmitted to the Google Gemini API during active generation requests.
Ephemeral State: Refreshing the browser clears all application state, including pasted documents and generated reports.
API Key Management: The GEMINI_API_KEY is injected at build time via environment variables. In a production deployment (like Google Cloud Run), this key should be restricted via Google Cloud IAM to only allow requests originating from the application's specific domain, preventing unauthorized use of the quota.
Cross-Site Scripting (XSS) Prevention: The react-markdown library is used to render AI output. By default, this library safely escapes raw HTML, preventing malicious scripts injected by the LLM (or via prompt injection) from executing in the user's browser.
10. Future Extensibility
The architecture is designed to be highly modular, allowing for rapid future expansion.
Adding New Painter Themes: To add a new theme, a developer simply adds a new object to the PAINTER_STYLES array in painter-styles.ts and defines the corresponding .theme-[name] CSS class in index.css with the desired HSL color variables.
Adding New LLM Models: New Gemini models (or even models from other providers if the service layer is expanded) can be added by updating the Model type in store.tsx and adding a new <SelectItem> in the App.tsx sidebar.
Adding New Workflow Tabs: A new feature can be added by creating a new component in src/components/tabs/, adding a new <TabsTrigger> in the App.tsx navigation bar, and mapping it to a <TabsContent> block.
11. Comprehensive Follow-Up Questions
To ensure the continued success, security, and scalability of the Agentic Medical Device Reviewer, the following 20 questions should be evaluated by the product and engineering teams:
Architecture & Performance
State Persistence: Currently, refreshing the page loses all data. Should we implement localStorage or IndexedDB caching for the global context and tab states to prevent accidental data loss?
Web Workers for Markdown: As generated reports grow to 3000+ words, markdown parsing on the main thread might cause UI stutter. Should we offload react-markdown rendering to a Web Worker?
Streaming Responses: The current implementation waits for the entire Gemini response before updating the UI. Should we implement the generateContentStream API to provide a typewriter-effect, reducing perceived latency for the user?
Bundle Size Optimization: We are importing the entirety of lucide-react and react-markdown. Have we audited the Vite build output to ensure tree-shaking is working correctly for these libraries?
PDF Parsing: The original prompt mentioned PDF uploads. Since this is a client-side app, should we integrate pdfjs-dist to extract text from PDFs directly in the browser before sending it to the LLM?
AI & Prompt Engineering
Search Grounding Costs: Google Search Grounding is enabled on Tab 1. What are the cost implications of this at scale, and should we provide a user toggle to disable it for simpler queries?
Context Window Limits: Medical device guidance documents can be hundreds of pages long. How should the application handle inputs that exceed the token limit of the selected Gemini model? Should we implement client-side chunking?
Hallucination Mitigation: In the "Gap Analysis" feature, how can we mathematically or programmatically verify that the AI isn't hallucinating regulatory requirements that don't exist in the TFDA guidelines?
Prompt Versioning: The prompts are currently hardcoded in the React components. Should we move these to a separate configuration file or a remote CMS so regulatory experts can tweak them without requiring a code deployment?
Checklist JSON Parsing: The regex fallback for JSON extraction in the Checklist feature is brittle. Should we utilize Gemini's responseSchema configuration to guarantee a strict JSON array output?
User Experience (UX) & Design
Mobile Responsiveness: The current layout uses a fixed 64-width sidebar. How should this UI adapt for tablet or mobile users? Should the sidebar collapse into a hamburger menu?
Accessibility (a11y): Have we audited the Shadcn UI components and our custom color themes (especially the high-contrast painter themes like Picasso) for WCAG AA color contrast compliance?
Export Formats: Currently, we only export to Markdown. Should we integrate a library like jspdf or html2pdf.js to allow users to download their final reports as formatted PDF documents?
Chat History Management: In the WOW Features tab, the chat history grows indefinitely. Should we implement a "Clear Chat" button and a mechanism to prune older messages to save context tokens?
Theme Persistence: Should the user's selected Painter Style and Dark/Light mode preference be saved to their browser preferences (localStorage) so it persists across sessions?
Security & Compliance
Data Confidentiality: Even though we don't store data, sending unreleased medical device specs to Google's API might violate corporate NDAs. Do we need to implement a warning modal advising users not to paste Proprietary Information (PII/PHI)?
Enterprise API Keys: Currently, the app uses a single environment API key. For a SaaS model, should we implement an OAuth flow allowing users to bring their own Google Cloud project API keys?
Content Moderation: Should we implement Gemini's safety settings to ensure the model doesn't generate inappropriate content, or should we lower the safety thresholds to ensure it doesn't falsely flag medical terminology as "gore"?
Domain-Specific (FDA/TFDA)
Template Updates: Regulatory templates change frequently. How will we maintain the DEFAULT_TEMPLATE in Tab 2? Should this be fetched dynamically from a GitHub repository or database?
Predicate Device Database: For 510(k) reviews, identifying predicate devices is crucial. Could we integrate a direct API call to the FDA's openFDA database to cross-reference the LLM's findings in real-time?
